## 一、数据合成与“冷启动” (Data Synthesis)

- **核心挑战：** 你有大量的静态 Q&A，但缺乏 Search-R1 需要的动态“思考+搜索”轨迹。

- **DeepResearch 参考：** 借鉴 DeepResearch 的思路，利用强模型（Teacher Model）+ 你的内部搜索引擎，将现有的 `<问题，答案>` 逆向扩展为带有 `<搜索动作，思维链>` 的完整轨迹。如何构建这个自动化的合成流水线是这一步的关键。

- **核心思路**：从“结果”反推“过程” (Reverse-Engineering the Process)
	DeepResearch 的核心在于模拟人类研究员的行为：`提出问题 -> 拆解意图 -> 构造查询 -> 阅读文档 -> 更新认知 -> 回答`。你的优势在于拥有“标准答案”和“目标知识”，这使得我们能进行极其高效的**有监督轨迹合成**。

### 1. 数据合成流水线设计

#### 针对 `<问题，目标知识，答案>` (黄金数据)

这是最有价值的部分。因为我们已知“为了回答这个问题，必须查到这段知识”。

- **合成目标：** 迫使模型生成能检索到“目标知识”的 Query，并基于该知识生成 CoT。

- **流程：**
    1. **Query 反向生成：** 输入 `<问题>` 和 `<目标知识>` 给 Teacher 模型，Prompt：_“为了回答这个问题并找到这段目标知识，作为保险专家，你应该在搜索引擎中输入什么检索词？”_ -> 产出 `<标准检索词>`。
    2. **受控推理生成：** 输入 `<问题>`、`<标准检索词>` 和 `<目标知识>`（假装是搜索结果）。
    3. **CoT 补全：** 让 Teacher 模型生成一段思维链：_“分析问题 -> 决定搜索（填入标准检索词） -> 读取结果（填入目标知识） -> 验证信息 -> 最终推理”_。

- **优势：** 100% 确保搜索行为的有效性，消除“无效搜索”的噪音。

#### 针对 `<问题，答案>` (白银数据)

只有答案，没有中间知识。我们需要 Teacher 模型通过“试错”来找到路径。

- **合成目标：** 重建从问题到答案的完整搜索路径。
    
- **流程（借鉴 DeepResearch）：**
    1. **Agent 自主搜索：** 让 Teacher 模型接入你的内部搜索引擎。
    2. **Rejection Sampling (拒绝采样)：**
        - Teacher 模型针对问题尝试生成 `<CoT + Search Query>`。
        - 执行搜索，获取 Top-K 结果。
        - Teacher 模型基于搜索结果生成 `<预测答案>`。
        - **校验器 (Verifier)：** 比较 `<预测答案>` 和 `<真实答案>`。
            - **Match:** 保留整条路径 `<问题, CoT, Search, Result, CoT, 答案>` 作为训练数据。
            - **Mismatch:** 丢弃或让 Teacher 模型基于错误反思重试（最多 N 次）。

- **保险特化：** 校验器不仅要比对文本相似度，最好能比对其中的关键实体（如：赔付比例、天数、险种名称）。

#### 针对 `<问题>` (青铜数据)

这部分数据量大，但没有验证标准。

- **合成目标：** 扩充数据的多样性（泛化能力）。

- **流程：**
    - 利用在策略 A/B 中训练好的 Teacher 模型，直接对这部分问题进行开放式回答。
    - **置信度过滤：** 只有当 Teacher 模型自我评估置信度极高，且引用了明确的内部知识库条目时，才保留数据。

#### 针对 `<简单问题>` (青铜数据)

加入**"无需搜索直接回答"** 的数据，比如简单的寒暄，教模型学会“适可而止”

### 2. Search-R1 风格的数据格式规范

#### 核心特性速览

1. **Role 适配:** 使用 `user` 角色承载 `<tool_output>`，利用标准 Loss Masking 机制防止模型背诵搜索结果。
2. **DeepResearch 协议:** 使用 JSON 格式的 `<tool_call>` 支持并行多路检索。
3. **动态推理 (Rolling Plan):** 在 `<think>` 过程中体现从“初步判断”到“发现新约束”的逻辑转折。
4. **内卷式合规 (Internal Grounding):** `[Fact Check]` 环节强制引用证据，但最终回答对用户不可见引用标记。

### 3. 开源数据集

为了训练 Search-R1 这种“思考+工具调用”的复杂模型，单一的开源数据集通常无法直接满足需求。你需要组合不同类型的开源数据集，分别针对“推理能力”、“工具调用格式”和“阅读理解”进行混合训练。

| **数据类型**            | **推荐数据集来源**             | **比例**  | **目的**              |
| ------------------- | ----------------------- | ------- | ------------------- |
| **Domain Specific** | **你自己的保险语料 (合成后)**      | **40%** | 核心业务能力，确保准确性        |
| **General CoT**     | Open-R1, Magpie         | **20%** | 激活模型的“思考”能力，防止变傻    |
| **Tool/Format**     | Glaive, xLAM (经过格式转换)   | **20%** | 强化 JSON 输出的鲁棒性，确保不崩 |
| **General RAG**     | HotpotQA, DuReader (中文) | **20%** | 提升从杂乱文档中提取答案的能力     |

具体实践建议：

- **下载 `Glaive-Function-Calling-v2`**：量大管饱，用来让模型学会“只要用户有查询意图，就扔出 JSON”。
- **下载 `DuReader` (中文)**：用来让模型适应中文语境下的“根据文档回答问题”。
- **使用 Teacher Model (Qwen-Max/DeepSeek) 进行“格式转写”**：
    - 不要直接用原始数据。
    - 写一个 Prompt，把 Glaive 和 DuReader 的数据作为输入，让 Teacher Model 按照我们定义好的 `<think>...<tool_call>` 格式重写一遍。
    - 这样你就得到了**数万条**符合 Search-R1 格式的、高质量的通用训练数据。

## 二、**分阶段训练策略 (Training Pipeline)**

- **阶段一 (SFT)：** 仅仅通过 SFT（监督微调）让模型学会格式和基本的搜索触发。

- **阶段二 (RL/RPO)：** 这是 Search-R1 的精髓。如何定义奖励函数（Reward Modeling）？比如：检索词是否准确命中了保险条款？最终答案是否符合合规要求？我们需要探讨如何在保险场景下设计 GRPO (Group Relative Policy Optimization) 或类似的强化学习策略。

### Phase 1. 格式与工具对齐 (Format & Tool Alignment)

- **目标：** 让 Base 模型“听懂”你的 JSON 格式，学会 `<think>` -> `<tool_call>` -> `<tool_response>` 的交互协议。
    
- **数据构成：**
    - **通用 Tool-Use 数据 (50%)**: 如 Glaive, xLAM（经过格式清洗）。
    - **通用 CoT 数据 (30%)**: 如 Open-R1（保持智商）。
    - **少量保险合成数据 (20%)**: 用于让模型预热保险词汇。

- **关键点：** 这个阶段不追求保险条款背得有多熟，只追求 **JSON 语法零错误** 和 **逻辑链路通顺**。
### Phase 2: 领域深度注入 (Domain Reasoning Injection)

- **目标：** 在掌握格式的基础上，注入我们之前合成的高质量“DeepResearch 风格”保险数据。

- **数据构成：**
    - **保险合成数据 (80%)**: 你用 Teacher Model 生成的那些高质量 JSONL。
    - **通用 CoT (10%)**: 防止灾难性遗忘（Catastrophic Forgetting）。
    - **通用 Tool-Use (10%)**: 保持工具调用的鲁棒性。

- **关键点：** 这个阶段的 Loss 重点在于 `<think>` 中的 **Fact Check** 和 `<tool_call>` 中的 **Query 构造精准度**。

### SFT 经验

在训练 Search-R1 这种 Agent 模型时，容易遇到以下“鬼故事”：

#### 1. "复读机" 现象 (Repetition Loop)
- **症状：** 模型一直在输出 `<think>`，或者一直发 `<tool_call>`，陷入死循环。
- **原因：** 训练数据中缺少“停止信号”或 `<tool_response>` 后的衔接不顺畅。
- **解决方案：** 确保每条数据都有明确的 EOS token (`<|im_end|>`)。并在 Phase 2 加入一定比例的 **"无需搜索直接回答"** 的数据（比如简单的寒暄），教模型学会“适可而止”。
#### 2. "幻觉引用" (Hallucinated Citations)
- **症状：** 模型学会了格式，但 Fact Check 里的 `Source ID` 是乱编的。
- **原因：** 模型把 `Source [1]` 当成了文本风格在学，而不是逻辑关联。
- **解决方案：** **负样本训练 (Negative Training)**（进阶）。
    - 构造一些数据，其中的 `<tool_response>` 是完全无关的内容。
    - 强制 Label 是：“无法回答”或“拒答”。
    - 这能逼迫模型真正去“看”内容，而不是猜答案。
#### 3. "搜索词退化" (Query Degeneration)
- **症状：** 模型只会搜“保险”两个字，不再构造具体的长尾 Query。
- **原因：** Teacher Model 生成的数据中，Query 过于简单，或者模型发现不管搜什么 Loss 都降得下去。
- **解决方案：** 提高 Phase 2 中复杂 Query 数据的权重。


### Phase 3: 进化“真正具备判断力”

简单来说，SFT 是“老师教一句，学生写一句”；而 GRPO 是“学生做 8 次题，老师给这 8 个答案打分，学生自己领悟哪种做法得分高”。
#### 1. 核心算法：GRPO (Group Relative Policy Optimization)

**为什么选择 GRPO？**
1. **省显存：** 不需要额外的 Critic 模型（和 Policy 模型一样大），只需要一个 Policy 模型。这对于你训练 4B 模型非常友好。
2. **适合推理：** 它通过对同一个问题采样多条路径（Group Sampling），鼓励模型通过“试错”发现更好的思维链。
3. **规则即奖励：** 保险场景下，很多标准是“硬规则”（如：JSON 必须合法、必须引用），GRPO 非常擅长利用这些规则作为奖励信号。
#### 2. 为保险 Search-R1 设计“奖励函数” (Reward Functions)

这是 RL 的灵魂。我们需要编写一组 Python 函数，用来给模型的每一次输出打分。

针对你的产品逻辑（DeepResearch 风格 + 隐式引用），建议设计以下 **4 个维度的奖励信号**：

1. 格式守门员 (Format Reward)
	- **目标：** 确保模型严格遵守 XML 和 JSON 协议，不崩坏。
	- **规则：**
	    - 是否包含 `<think>`, `<tool_call>` 等标签？
	    - `<tool_call>` 里的内容是否为合法的 JSON？
	    - `queries` 是否为列表？
	- **奖励：** 满足得 +1，JSON 解析失败直接 -1（强惩罚）。

 2. 引用一致性奖励 (Citation Consistency Reward)
	- **目标：** 防止幻觉，确保 Fact Check 不是瞎写的。
	- **规则：** 解析 `<think>` 结尾的 `[Dynamic Fact Check]`。
	    - 检查每一个 `Source X` 是否在 `<tool_response>` 中真实存在？（存在得 +0.5）
		- **进阶：** 检查 Verified 的结论文字，与 Source 原文是否有 **关键词重合 (Keyword Overlap)**？（重合度高得 +0.5）
	- **作用：** 逼迫模型“有几分证据说几分话”。

3. “净身”奖励 (Clean Answer Reward)
	- **目标：** 强约束最终回答里不能出现 `[1]`。
	- **规则：** 检查 `</think>` 之后的文本。
	    - 使用正则 `\[\d+\]` 或 `Source \d` 扫描。
	    - **如果发现：** 给予 **-1** 的惩罚（Bad Case）。
	    - **如果没有：** 给予 **+0.5** 的奖励。
	- **作用：** 完美解决你“用户侧不可见引用”的需求。
    
4. 拒答奖励 (Rejection Reward)

	- **目标：** 鼓励模型在查不到资料时承认不知道。
	- **规则：** 如果 `<tool_response>` 是空的或者相关度极低（可以在环境侧预埋 flag），而模型输出了“无法确定”、“建议咨询”等关键词。
	- **奖励：** 给予 **+1**。防止模型在没资料时强行编造。
#### 3. 训练流程设计 (The Pipeline)

在 GRPO 训练中，我们需要一个“模拟环境”。因为在线调用你的真实搜索引擎太慢了，建议采用 **Offline-GRPO** 或 **Cached Search**。
##### 步骤 1: 准备 Query 集 (Prompts Only)
你只需要大量的 `<问题>`，不需要答案。
- 来源：你已有的“大量<问题>”数据集。
- 数量：建议准备 5k - 10k 条高质量保险问题。

##### 步骤 2: 静态缓存搜索环境 (Mock Environment)
为了训练加速，不要让模型真去搜。
1. 拿这 10k 个问题，先跑一遍你的搜索引擎，把 Top-K 结果存下来的。
2. 构建一个 `(Question) -> (Cached Search Results)` 的映射表。
3. **Hack 技巧：** 在训练时，无论模型生成什么检索词（只要不太离谱），我们都把这就对应的“标准搜索结果”喂给它。
    - _为什么？_ 因为我们 RL 的重点是训练模型**“拿到结果后如何推理”**以及**“如何合规回答”**，而不是训练检索词生成（那个在 SFT 阶段已经做得差不多了）。

##### 步骤 3: 训练循环 (Training Loop)

1. **Rollout (采样):**
    - 输入：`User Question`
    - 模型生成：`<think>...<tool_call>...`
    - 环境反馈：填入 Cached Search Results (`<tool_response>`)
    - 模型继续生成：`<think>...Fact Check...</think> Final Answer`
    - **重复 8 次**（Group Size = 8），得到 8 个完整的轨迹。
2. **Evaluation (打分):**
    - 利用上面的 **4 个奖励函数**，对这 8 个轨迹分别打分。
    - 比如：
        - 轨迹 A：JSON 错了 (-1分)
        - 轨迹 B：引用对了，但最后漏了 `[1]` 给用户看 (-0.5分)
        - 轨迹 C：完美引用，且回答干净 (+2分)
3. **Optimization (更新):**
    - 计算 Advantage（优势值）：轨迹 C 比平均分高，鼓励它；轨迹 A 比平均分低，抑制它。
    - 更新模型参数。
#### 5. 训练监控指标 (Monitoring)

除了看 Training Loss，建议在 WandB 中重点监控以下 Token 的准确率：
1. **Tag Accuracy:** `<tool_call>`, `</think>`, `}` 这些特殊结构符的预测准确率。如果这些崩了，JSON 就会解析失败。
2. **Citation Token Accuracy:** 监控 `Source`, `Verified` 等关键词的 Loss 变化。

当 RL 开始跑之后，你会观察到非常有趣的现象（Aha Moments）：

    2. **Fact Check 真实性** (Anti-Hallucination)。

## 三、**保险领域的评估指标 (Domain-Specific Evaluation)**

- **准确性 vs. 幻觉：** 保险客服对错误的容忍度极低。

- **指标设计：** 除了通用的 BLEU/ROUGE，我们需要设计针对“引用准确率”（Citation Precision）和“拒答机制”（Rejection Rate）的指标，确保模型在查不到条款时不会胡编乱造。

### 1. 评估架构：三个维度 (The 3-Level Evaluation)

我们不能只看结果，要看“结果、过程、风控”三个层面。
#### Level 1: 结果质量 (Outcome Quality) —— "答对了吗？"

这是给最终用户看的，决定了产品能不能上线。
- **准确性 (Accuracy):** 答案是否符合保险条款？（这是生死线）
- **完整性 (Completeness):** 是否覆盖了用户问题中的所有约束条件（如：既往症、免赔额、异地就医）？
- **拒答率 (Rejection Rate):** 遇到完全超纲的问题（如“怎么制造炸弹”或“查询非本公司产品后台数据”），是否正确拒绝？
#### Level 2: 过程质量 (Process Quality) —— "想对了吗？"

这是给算法工程师看的，用于 Debug 模型智商。
- **搜索有效性 (Search Efficacy):** `<tool_call>` 里的 Query 是否真的能搜到东西？（检索词构建能力）
- **幻觉指数 (Hallucination Index):** `<think>` 里的 `Fact Check` 引用是否真实存在？（是否存在“瞎引用”）
- **路径效率 (Trajectory Efficiency):** 是否存在“搜索->没看懂->重复搜索->还是没看懂”的死循环？
#### Level 3: 业务合规 (Business Compliance) —— "话术对了吗？"

这是给保险业务专家看的。
- **合规性 (Compliance):** 是否出现了绝对禁语（如“肯定能赔”、“百分百报销”）？
- **引用隐身 (Citation Invisibility):** 最终回答里是否干净，没有 `[1]` 这种符号？
### 2. 具体的评估指标与计算方法

建议构建一个 **自动化评测集 (Benchmark)**，包含 200-500 条高质量标注数据。

|**指标维度**|**指标名称**|**计算方法/Prompt 逻辑**|**目标值**|
|---|---|---|---|
|**结果**|**Exact Match (业务点)**|人工标注答案包含的关键点（如“60%”、“免赔额”）。用脚本检测模型回答是否包含这些关键词。|> 90%|
|**结果**|**LLM-as-a-Judge (GPT-4评分)**|给 GPT-4 输入 `<标准条款>`、`<用户问题>`、`<模型回答>`。Prompt: _"请判断回答是否违背条款？是否误导用户？打分1-5"_。|> 4.5|
|**过程**|**Citation Precision (引用准确率)**|提取 `<think>` 中的 `Verified (Source X)`。检测该 Source X 的文本中是否真的包含支撑结论的关键词。|> 95%|
|**过程**|**Search Success Rate (搜索成功率)**|模型生成的 Query 在你的搜索引擎中，Top-3 结果的相关性得分（Relevance Score）平均值。|-|
|**合规**|**Safe-Word Check (禁语检测)**|建立一个“黑名单词库”（如：全额赔、保本、收益率），扫描最终回答。|0%|
### 3. 如何构建“自动化评估管线” (Eval Pipeline)

手动看 Log 太慢了，你需要一个自动化的脚本。
#### 步骤 1: 准备测试集 (Golden Test Set)
你需要 200 条数据，结构如下：

### 4. 针对 Search-R1 的特殊评估：轨迹可视化

对于 Agent 模型，**Bad Case 分析**比分数更重要。建议开发一个简单的 HTML 页面，可视化展示模型的“心路历程”：
- ✅ **Good Case:**
    - Query: "高血压能买吗" -> Search: "产品名 智能核保 高血压" -> Result: "2级以下可保" -> Answer: "2级以下有机会"。
    - _(评价：路径清晰，一击即中)_
- ❌ **Bad Case (死循环):**
    - Query: "高血压" -> Search: "高血压定义" (太泛) -> Result: (无用信息) -> Search: "高血压" (重复) -> ...
    - _(评价：Query 构造能力差，需加强 Phase 2 SFT)_

    - Query: (无) -> Answer: "建议您咨询客服。"
    - _(评价：RL 惩罚过重，导致模型不敢搜了)_
### 总结
评估 Search-R1 的效果，不能只看“聊得好不好”，核心是看 **“搜得准不准”** 和 **“信得过不过”**。

## 📅 阶段三：强化学习 (RL/GRPO - The Expert)

**优先级：P1**

**目标：** 通过规则奖励解决“幻觉引用”和“回答带角标”的问题。

### 3.1 任务描述

使用 `trl` 库编写 `train_grpo.py`。**这是工程难度最大的一步。**

### 3.2 核心代码逻辑 (给 AI 的 Coding 指令)

你需要实现自定义的 `GRPOTrainer` 和 3 个核心 `Reward Functions`。

**1. 环境模拟 (Cached Environment):**

- 不要在 RL 循环里实时调用 HTTP 搜索（太慢）。
    
- 加载一个 `search_cache.json` (Key=Question, Value=TopK Results)。
    
- 如果模型生成的 Query 在 Cache 里找不到，给予一个微小的惩罚并返回“未找到相关信息”。
    

**2. 奖励函数设计 (Python Code):**

- `reward_format(completions)`: 检查是否包含 `<think>`, `<tool_call>`, `</think>`。JSON 是否合法。 (+1.0 / -1.0)
    
- `reward_clean_answer(completions)`: 使用正则 `r"\[\d+\]|Source \d"` 扫描 `</think>` 后的文本。如果**没有**匹配到，得 +1.0；如果匹配到，得 -0.5。
    
- `reward_citation(completions)`: 提取 `<think>` 里的 `Verified (Source X)`。检查 Source X 的文本与 Claim 是否有 Token 重叠。 (难度较大，可选，先做前两个)。
    

**3. TRL 配置:**

Python

```
# train_grpo.py 片段
training_args = GRPOConfig(
    num_generations=8,      # Group Size
    max_completion_length=2048,
    beta=0.04,              # KL 惩罚系数
)
trainer = GRPOTrainer(
    model=sft_model,        # 加载阶段二的模型
    reward_funcs=[reward_format, reward_clean_answer],
    args=training_args,
    train_dataset=prompts_only_dataset
)
```

### ✅ 阶段三验收点 (DoD)

- [ ] 模型输出的最终回答中，`[1]` 这种引用标记完全消失。
    
- [ ] 即使在没有搜索结果的情况下，模型也能触发“拒答”逻辑（需配合拒答奖励）。
    
- [ ] 模型的 Thinking 过程包含 `[Dynamic Fact Check]`。

## 📅 阶段四：推理与评估 (Inference & Eval)

**优先级：P1**

### 4.1 任务描述

### 4.2 推理循环逻辑 (Pseudo-Code)

```Python
def chat(user_query):
    messages = [{"role": "user", "content": user_query}]
    
    # Round 1: Think & Search
    resp1 = model.generate(messages, stop=["</tool_call>"])
    if "<tool_call>" in resp1:
        # 解析 JSON -> 执行真实搜索 -> 拼接结果
        tool_res = real_search_engine(extract_query(resp1))
        messages.append({"role": "assistant", "content": resp1 + "</tool_call>"})
        messages.append({"role": "user", "content": f"<tool_response>{tool_res}</tool_response>"})
        
        # Round 2: Re-Think & Answer
        resp2 = model.generate(messages)
        return clean_tags(resp2) # 只返回 </think> 后的内容
    else:
        return resp1
```

# 阶段一冷启动


这是一个非常典型的**冷启动**场景。你手里其实有一座金矿（尤其是那批 `<问题, 目标知识, 答案>`），只要通过**“逆向合成” (Hindsight Generation)** 的策略，就可以在**不调用真实搜索引擎**的情况下，极速构建出第一批高质量 Search-R1 训练数据。

核心思路是：**“伪造过程”**。既然你已经有了“目标知识”（即搜索结果）和“答案”，你只需要让 Teacher 模型（GPT-4/Qwen-Max）**倒推**出“我是怎么想到要搜这个的”以及“我是怎么查到这个的”。

以下是基于你现有资源的**优先级排序**和**具体合成方案**：

---

### 🚀 策略一：挖掘金矿 —— 利用 `<问题, 目标知识, 答案>` (Priority P0)

这是你最有价值的资源。因为“目标知识”本质上就是完美的“搜索结果”。

我们不需要真的去搜，只需要把“目标知识”**塞进** `<tool_response>` 里，然后让模型补全前后的逻辑。

**合成逻辑（Hindsight Relabeling）：**

1. **Input:** `Q`, `Doc` (目标知识), `A`.
2. **Task:** 请 Teacher 模型生成：
    - `<think>_1`: 为什么需要这个 Doc？ -> 生成 `Query`。
    - `<tool_call>`: 包含这个 `Query`。
    - `<think>_2`: 看到 `Doc` 后如何推理出 `A`。

**Teacher Prompt 模板 (直接拿去跑):**

```Python
SYSTEM_PROMPT = """
你是一个数据合成专家。我给你一个“问题”、一段“参考资料”和一个“标准答案”。
你的任务是还原一个 Search-R1 风格的推理过程。

请生成以下 JSONL 格式的对话历史：
1. User: 提出问题。
2. Assistant: 
   - <think>: 分析问题，决定需要搜索什么内容才能得到该资料。
   - <tool_call>: 生成一个能搜到该资料的检索词(queries)。
3. User: 
   - <tool_response>: 直接填入我提供的“参考资料”。
4. Assistant: 
   - <think>: 阅读资料，进行事实核查，推导答案。
   - Final Answer: 填入我提供的“标准答案”（可适当润色使其更自然）。

要求：
- <tool_response> 的 role 必须是 "user"。
- 保持逻辑连贯，好像你真的是刚搜到这个资料一样。
"""

USER_PROMPT = f"""
问题: {question}
参考资料: {target_knowledge}
标准答案: {answer}
"""
```

**✅ 预期产出：** 50% - 70% 的核心 SFT 数据。质量极高，因为“搜索结果”绝对相关。

---

### 🚀 策略二：扩充基础 —— 利用 `FAQ` 和 `<问题, 答案>` (Priority P1)

这部分数据只有 Q 和 A，缺“中间过程”和“证据”。

**策略：** 让 Teacher 模型**“自问自查”**。

**合成逻辑：**

1. **Input:** `Q`, `A`.
2. **Task:** Teacher，请你为了回答这个 `Q`，去构造一个虚拟的 `Search Query`，然后**根据这个 `A` 逆向编造**一段假的 `<tool_response>` (假条款)，最后输出 `A`。

**注意：** 虽然这里 `<tool_response>` 是编的，但只要 Teacher 够强（如 GPT-4），编出来的条款通常符合逻辑。这对训练模型的“格式”和“引用能力”非常有用。

**Teacher Prompt 模板:**

```Python
SYSTEM_PROMPT = """
我给你一个保险问题和答案。请你伪造一个完整的“搜索-推理”过程。
1. 根据问题，生成合理的 <tool_call> 搜索关键词。
2. 即使你没有联网，也请根据“答案”的内容，**编造**一段看起来真实的保险条款或搜索片段，放入 <tool_response> 中。
3. 最后输出原答案。

关键点：训练模型学会“先引用 <tool_response> 里的内容，再回答”。
"""
```

**✅ 预期产出：** 20% - 30% 的补充数据。用于增加数据的多样性。

---

### 🚀 策略三：种子发芽 —— 利用 `<问题, 思维链, 检索词>` (Priority P2)

这部分数据量少，不要直接用来训练，用来做 **Few-Shot Prompt 的示例**。

**用法：**

将这几条高质量数据写进上述“策略一”和“策略二”的 System Prompt 里，作为 `Examples`。

- 告诉 Teacher：“看，我就要生成这种风格的数据，请模仿它。”
- 这能显著提升合成数据的统一性和质量。

---

### 🚀 策略四：格式对齐 —— 利用 开源数据集 (Priority P3)

你需要让模型学会 `<think>`, `<tool_call>` 这些 XML 标签的语法。不要只用保险数据，防止过拟合。

**推荐数据集：**

1. **Glaive-Function-Calling-v2:** 质量很高，全是工具调用。
    - _处理：_ 写个脚本，把它的 JSON 格式转成你的 XML 格式。
2. **Open-R1 (Math/Reasoning):**
    - _处理：_ 抽取一部分，去掉 Tool Call，只保留 CoT。这用于防止模型变笨（保持通用推理能力）。

**✅ 预期产出：** 10% 的通用数据。

---

### ⚡️ 极速执行清单 (Action Plan)

假设你现在就要开始跑脚本，请按这个顺序：

1. **Day 1 上午：清洗数据**
    - 把 `<问题, 目标知识, 答案>` 清洗为 JSONL。
    - 把 `<问题, 思维链, 检索词>` 整理成 prompt_examples.txt。

2. **Day 1 下午：跑脚本 (策略一)**
    - 写一个 Python 脚本，并发调用 OpenAI/DeepSeek/Qwen API。
    - 输入：策略一的数据。
    - Prompt：带上 prompt_examples.txt。
    - **目标：** 快速生成 1000 条“完美轨迹”数据。

3. **Day 2 上午：补充通用数据 (策略四)**
    - 下载 Glaive 数据集，随机采样 500 条。
    - 写个正则替换脚本，转成你的 XML 格式。

4. **Day 2 下午：合并与 SFT**
    - **Dataset = 1000条(策略一) + 500条(策略四)**。
    - 直接扔进 LLaMA-Factory 开始训练。


### 💡 避坑指南

- **不要用 `<问题>` (无答案) 的数据：** 在第一批 SFT 中，这种数据处理成本太高（需要 Teacher 真的去联网搜），性价比低。留到下一阶段做 RL 或者 DeepResearch 增强时再用。
    
- **FAQ 的陷阱：** FAQ 通常是很短的单轮问答。合成时要强制 Teacher **“加戏”**，强行把简单的 FAQ 扩展成“思考-查证-回答”的过程，否则模型学不会深度思考。
    

**总结：** 你的核心武器是那批 **`<问题, 目标知识, 答案>`**。用“逆向合成法”，你不需要写爬虫，不需要调搜索 API，一天之内就能造出顶级的 Search-R1 训练数据。
